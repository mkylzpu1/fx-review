FXトレードの振り返り・学習Webサービス「FXレビュー」を、添付の `project-template` をベースに実装するための指示書。
実装するAIは、**最初にこのファイルと `README.md`（テンプレート側のAI Development Instructions）を最後まで読むこと。**

1. テンプレート `README.md` の鉄則・コーディングルール（ディレクトリ構成、責務分離、共通処理の再利用）

## 1. ゴールと範囲

自分が行ったFXトレードについて、次を記録して振り返れるWebサービス。

- 利確（TP）・損切り（SL）・エントリー根拠・感情・ルール遵守を記録し、結果（pips / 円 / R倍数）を見られる
- トレード詳細で、**エントリー時点の 1m / 5m / 15m / 1h / 4h / 1d 足**を切り替えて見られ、任意の期間のEMAをチャートに重ねられる
- 全データをまとめて出力でき、**AIに貼り付けて「どう改善すべきか」を分析してもらえる**内容になっている
- AIの回答を貼り付けて改善案を取り出し、ルール化し、10件で効果を検証するループが回せる
- 楽天FX証券の約定履歴CSVを複数ファイルまとめて取り込める

利用者は当面、持ち主1人（ただし認証付きのマルチユーザー構造で作る。全テーブルに `user_id`）。

### 確定済みの前提（持ち主の回答）

- 対象通貨ペアは **USDJPYのみ**（円が絡まないペアや為替換算は扱わない）。設定の通貨ペア初期データは USDJPY 1件（pip幅 0.01、1 lot = 1万通貨・1lot・1pipあたり100円）
- **1トレード = 新規1回 + 決済1回**。ナンピン・買い増し・分割決済は考慮しない（CSVでペアにできない約定は取り込みエラーとして表示する）
- **スワップ・手数料は扱わない**（列もUIも作らない）。損益は約定履歴CSVの `取引損益（円換算）`、手入力は価格差から計算した値のみ（§9.1）
- **SL・TP・根拠・感情・確信度・メモ・ルールチェックはすべて任意項目**。全件に入力する前提にしない。トレードとして必須なのは、方向・ロット・エントリー日時・エントリー価格（決済済みなら決済日時・決済価格）だけ。未入力のときの扱いは§9.7
- **口座は1つ**（口座の概念をDBに持たない）
- **当面は自分専用**。ただし将来は他の人も使うため、全テーブルの `user_id` と所有者チェックは省略しない。利用規約・プライバシー・ランディングページは今回作らない

### やらないこと（今回の対象外）

- **Terraform対応は今回やらない。** `terraform/` ディレクトリと、`.github/workflows/` 内のTerraform関連ワークフローには触れない（編集・削除・移動をしない）。STG/PRDへのデプロイは今回の範囲外。
- ローカル開発（Docker PostgreSQL + AWS SAM + Vite）で動くところまでを完成とする。
- MT5取り込み（画面には「準備中」として表示するだけ）。
- 証券会社APIとの連携、自動売買、リアルタイム価格。

## 2. ベースコードの扱い

### 2.1 まず調査する（README 鉄則1）

実装前に必ず読む。

- `README.md`、`docs/アーキテクチャ.md`、`docs/API設計.md`、`docs/DB設計.md`
- `backend/src/lib/*`（`cognito`, `db`, `errors`, `logger`, `response`, `validate`）
- `backend/src/handlers/example/index.ts`、`handlers/auth/*`、`stores/userStore.ts`
- `frontend/src/services/apiClient.ts`、`features/auth/*`、`components/layout/AppLayout.tsx`、`constants/routes.ts`、`App.tsx`

### 2.2 守ること

| 項目 | ルール |
|------|--------|
| 構成 | Backend は `handlers/`（薄く）→ `services/`（ロジック）→ `stores/`（SQLのみ）。Frontend は `features/<feature>/{pages,components,hooks,utils}` |
| 共通処理 | `verifyAuth` / `success` / `errorResponse` / `parseBody` / `parseQuery` / `logger` / `sql` / `apiClient` / `ErrorAlert` / `LoadingSpinner` を必ず使う。自前で作り直さない |
| エラー | `lib/errors.ts` のクラスを使う。ハンドラーの catch は必ず `errorResponse(e)` |
| DB | マイグレーションは `backend/db/migrations/` に連番で追加（`002_...` から）。**既存の `001_create_users.sql` は編集しない。** カラムは `snake_case`、storeのSQLで `camelCase` にエイリアス |
| 型 | `any` 禁止。型は使う場所の近くに置き、複数箇所で使うものだけ `types/` へ |
| ファイル | 300行を超えたら分割。UIとロジックを混ぜない。同じ処理が2箇所に出たら共通化 |
| 新API | `docs/API設計.md` に追記 → ハンドラー実装 → `backend/build.mjs` の `handlers` 配列に追加 → `sam/template.yaml` にリソース追加 → フロントのフック実装（この順） |
| 認証モジュール | `features/auth/` は基本的に変更しない（§5 の方針で必要な最小限だけ） |

### 2.3 テンプレートから変えてよいもの

- `AppLayout.tsx` は**置き換えてよい**（デザインはダークテーマの上部ナビで、テンプレートの青いサイドバーとは別物）。`useAuthContext` の使い方は踏襲する。
- `index.css` / `tailwind.config.ts` にデザイントークンを追加する。
- `handlers/example/` は、実装が済んだら削除してよい。

### 2.4 追加してよい依存

| パッケージ | 用途 |
|-----------|------|
| `lightweight-charts`（frontend） | ローソク足チャート |
| 必要なら CSV/文字コード処理用の小さなライブラリ（backend） | 楽天CSVのパース。追加前に持ち主へ報告 |

上記以外の新規依存は、必要性を説明してから追加する。

### 2.5 Git

- `develop` から `feature/fx-review-<phase>` を切って作業する。`develop` / `main` へ直接pushしない。
- フェーズごとにPRを分ける（§14）。PRの前に `npm run quality` と `npm run test` を frontend / backend の両方で通す。

## 5. 認証方針

### 5.1 ローカル開発は固定ユーザー（Cognito・Googleの設定は不要）

- Backend: `lib/cognito.ts` の `verifyAuth` は `IS_LOCAL=true`（`backend/.env.local`）のとき、**固定ユーザー（`userId: "local-user-id"`、`local@example.com`、`Local User`）を返してJWT検証を省く**。テンプレートに実装済みなので、そのまま使う
- Frontend: テンプレートには同等の迂回が**無い**（`useAuth` は Amplify 前提でログイン画面に飛ばされる）。**P0で追加する**:
  - `VITE_LOCAL_AUTH=true` のとき `useAuth` が Amplify を呼ばず、固定ユーザー（Backendと同じ `local-user-id`）を返す。`RequireAuth` はそれで通す。`LoginPage` へは遷移しない
  - **本番ビルドでは無効**にする: `import.meta.env.DEV` が真のときだけ有効。PRODビルドで `VITE_LOCAL_AUTH=true` が設定されていたらビルドまたは起動時にエラーにする
  - `.env.example` に `VITE_LOCAL_AUTH=true` を追記し、`README` のローカル手順を「Cognitoは不要」に更新する
- この変更は `features/auth/` のうち `useAuth.ts` / `RequireAuth.tsx` に限る。他の認証コードは変更しない

### 5.2 STG/PRD（今回の対象外）の認証

テンプレートは **Cognito + Google OAuth のみ**。デザインのログイン / アカウント作成 / パスワード再設定 / アカウント設定のメール・パスワード変更は **メール＋パスワード前提**で描いてあるが、次の方針で実装する（持ち主から変更の指示がなければ）:

- ログインは Google OAuth のみ（テンプレートの実装を使い、`LoginPage` の見た目と文言だけダークテーマに合わせる）
- 作らない画面: アカウント作成、パスワード再設定、メールアドレス変更、パスワード変更
- アカウント画面（`/account`）は、名前・メール・アイコンの表示（読み取り専用）、ログアウト、退会のみ。退会は既存の `DELETE /auth/me`。デザインの退会確認（「退会」と入力して実行、先にエクスポートの導線）は踏襲する
- 初回ログイン時は `GET /auth/me` がユーザーを作成する。そのあと `account_settings` が未作成ならオンボーディングへ遷移させる
- 「ログインの有効期限が切れました」ダイアログは実装する（入力中の内容はログイン後に戻す）。ローカル固定ユーザー時は出さない

メール＋パスワードにする場合は Cognito 側の変更が必要になりTerraform対象外を超えるため、**勝手に変更せず質問する。**

## 7. 画面ごとの要点

詳細な見た目はデザインを見ること。ここは**落としてはいけない振る舞い**の一覧。

**共通: SL・TP・根拠・感情・確信度・メモ・ルールチェックは任意**。デザインで必須に見える箇所（記録画面のSL、発注前チェックなど）も、**未入力のまま保存できる**ようにする。入力された場合だけ検証する（SLの向き、RRの警告など）。SLが無いときは、想定リスク・リスクリワード・ルールとの照合は「SLを入れると計算されます」と淡く表示する。

### トレード記録 `/trades/new`
- 6セクション: 基本情報 → 価格の計画 → エントリー根拠 → 発注前チェック → いまの状態 → 決済（あとで入力可）
- 基本情報: 通貨ペア（設定の候補から選択）、方向（買い/売り）、エントリー日時（JST）、ロット
- 価格: エントリー・SL・TP と、SLの理由・TPの理由
- 右側に「計画のサマリー」（リスクリワード、想定リスク円と口座に対する%、想定利益）と「ルールとの照合」を**入力に合わせてリアルタイム表示**。口座残高は設定の値で計算
- 発注前チェックはルール画面の有効なルールが項目になる。結果は保存してルール遵守に反映
- 保存ボタン: 「保存してチャートを見る」「下書きとして保存」。保存後、チャートは `GET /candles` で取得して表示する（§10。足が未同期の期間は失敗表示になる）
- **入力エラー**（デザインの通知・確認ボード準拠）: 項目直下に赤枠＋理由1行。買いのSLはエントリーより低く、売りは高く。ロットは0より大きく。**RRが設定の最低値未満は警告のみで保存は可能**

### トレード詳細 `/trades/:id`
- 左: 直近トレードの一覧（直近6件の勝率・PF・平均R、すべて/勝ち/負けの絞り込み）。右: 選択トレード
- チャート: 時間足 `1m 5m 15m 1h 4h 1d` を切り替え、EMAをチップでON/OFF（期間追加可）、「エントリー後の値動き」表示のON/OFF、TP・エントリー・SLを破線で表示
- 結果: pips、円、R倍数、「計画は +x.xR」、保有中の最大/最小（MFE/MAE）、決済後の最大到達
- 計画と結果、エントリー根拠（タグ＋メモ）、SL/TPの理由、ルール遵守チェック（OK/NG）、振り返りメモ（確信度 n/5、感情、気づき、次回のルール）、「編集」
- チャートが取得できない場合・データが無い場合の表示はデザイン（チャート読み込み失敗）どおり。**チャートが無くても価格・根拠・結果は見られる**

### トレード編集・決済入力 `/trades/:id/edit`
- 決済日時・決済価格・決済の仕方（利確到達 / 損切り到達 / 手動決済 / 建値決済）を入力すると、**結果の見込み（pips・R）を即時表示**
- SL・TP・根拠・感情・守ったルールを後から書き足せる（CSV取り込み分に使う）
- 「保存して次の未入力へ」「保存」「キャンセル」。未保存で離れるときは確認ダイアログ（破棄して移動 / 下書き保存 / 編集を続ける）

### 未入力キュー `/trades/queue`
- **入力は任意**なので、このキューは「書き足したいトレードを探して順に開く」ための補助画面（入力を促す画面ではない）。件数の強調や警告色は使わない
- 「入力のないトレード」件数、入力の進み具合（入力あり/全件）、絞り込み（すべて / SL・TP未入力 / 根拠なし / 未決済 / 負けトレード / 損失が大きい順）。**数百件でも使えるよう、並べ替え（日時・損益）を付ける**
- 各行に未入力項目のタグ。行クリックで編集画面。「新しい順に1件ずつ開く」で先頭から順に開く。**行ごとの「あとで」「今はしない」操作は作らない**（入力しないトレードはそのまま放置してよい）
- 「入力のない」の定義はサーバー側の1か所で決める（`trades` サービス。例: SL/TP/根拠タグがいずれも空、または未決済）

### ルール `/rules` と `/rules/:id`
- 一覧: 追加・編集・有効/無効（無効化の確認ダイアログあり。**過去の判定は残す**）・並べ替え
- 詳細: 直近4週の遵守率、守った時 / 破った時の平均R、遵守率の週次推移、破ったトレード一覧
- ルールの判定: 自動判定できるもの（SLの有無 / リスクが口座の上限%以内 / 計画のTPまで保持）は `auto_key` で判定し、それ以外は手動チェック
- 学習メモから「ルールに追加」されたルールは「検証中」。ルール化後10件たまったら前後の成績を比べる（§9.5）

### 統計 `/stats`
- 期間（過去90日 / 過去30日 / 今月 / すべて）と通貨ペアで絞り込み

### 週次レビュー `/stats/weekly`

- 「計画どおりに持っていたら」: TPまで保持しなかった手動決済を計画どおり決済したと仮定した合計R（実際との差と、そのときの感情タグ）

- 来週守るルールを1つ選ぶ、1週間のふりかえり、「保存して学習メモに残す」「この週をAIに出力」

### 学習メモ `/notes`、AI分析の結果ビュー `/notes/:id`
- 「AIの回答を貼り付ける」: 使ったAI（Claude / ChatGPT / Gemini / その他）、渡したデータの範囲を選び、貼り付けた回答から**改善案を1行ずつ取り出して保存**
- メモ一覧は種別（AIの分析 / 自分の気づき）、検証中で絞り込み。自分の気づきはトレード詳細の「次回のルール」から作れる
- 各改善案に状態: ルール化済み / 検証中 / 要検証（n=）。「ルールに追加」で `rules` に作成
- 「検証中の改善ルール」: ルール化後の件数 / 目標10件、守った時・破った時の平均R、ルール前の成績との比較
- 結果ビュー: 回答の要約、勝ち負けを分けた条件、改善提案（優先度）、原文を見る、学習メモに追加。**回答は自由文なので、構造化は貼り付け時の簡易パース（番号付き行・箇条書きの抽出）で行い、パースできない部分は原文表示にフォールバックする**（LLM呼び出しはしない）

### エクスポート `/export`
- 対象期間、含める項目のON/OFF、形式（Markdown / CSV / JSON）、「全データをコピー」「ダウンロード」、プレビュー

## 9. ドメインロジック

計算は `backend/src/services/` に純粋関数として置き、**ユニットテストを必ず書く**（フロントで同じ計算が必要な箇所は `frontend/src/utils/` に同等の純粋関数を置き、同じテストケースを共有する）。

### 9.1 価格・損益
- `slPips = |entry − sl| / pipSize`、`tpPips = |tp − entry| / pipSize`
- `pips = (exit − entry) / pipSize`（売りは符号反転）
- `R = pips / slPips`（SLが無いトレードは `null`）
- `RR = tpPips / slPips`
- `想定リスク円 = slPips × pipValueJpyPerLot × lots`、口座に対する% = 想定リスク円 / 口座残高
- 円損益（価格損益）: CSV由来はCSVの `取引損益（円換算）`、手入力は `pips × pipValueJpyPerLot × lots`
- スワップ・手数料は考慮しない（損益にも含めない）
- 保有時間 = `exit_at − entry_at`
- 検証: 買いは `sl < entry`、売りは `sl > entry`。TPは逆

### 9.2 MFE / MAE / 決済後の最大到達
- 1m足（無ければ取得できた最小時間足）で、保有中の最大含み益 / 最大含み損（pips）を計算
- 決済後の最大到達は、決済後 `chart_bars_after` 本の範囲で、有利方向への最大到達（pips）

### 9.3 ルール判定
- `sl_set`: SLが入っている
- `risk_within_limit`: 想定リスク% ≤ `max_risk_pct`
- `hold_to_tp`: TPが設定済みで `exit_method = manual` なら NG、`tp` なら OK、`sl` なら `na`
- 「逸脱」= 有効なルールに1つでも `ng` がある
- 「計画どおりR」（週次）: `hold_to_tp` がNGのトレードの R を `RR` に置き換えて合計

### 9.4 統計・「データから見えること」
- 累積R、最大DD（累積Rのピークからの最大下落と区間）、勝率、PF（総利益R/総損失R）、平均R、最大連敗
- セッション判定はエントリー時刻（設定のタイムゾーン）で分類する。**区分は定数1か所（`constants/sessions.ts`）に置く**。初期値は東京 9〜15時、ロンドン 16〜21時、NY 21〜翌6時（JST）とし、夏時間は今回は考慮しない（仮値。確定したら持ち主が直す）
- 強み/弱み/要検証の判定: 区分ごとに `n` と平均Rを出し、`n ≥ 15` なら平均Rの符号で強み/弱み、`n < 15` は「要検証」（デザインの文言「あと10件ほど記録してから判断」）。閾値は定数化
- 件数が少ない集計には必ず注意書きを付ける（断定しない）

### 9.5 ルール化した改善案の検証
- ルール作成時に `validation_started_at` を記録し、以後のトレードを数える。目標件数（既定10）に達したら「結果を見て判定する」を出す
- 表示: ルール前の平均R / ルール後の平均R、守った時・破った時の平均R

### 9.6 重複判定（取り込み）
- `source_key = sha256(source + entry_at + pair + side + lots + entry_price)` を基本とする（楽天CSVの項目に合わせて確定する）。取り込み時、既存と一致するものは「取り込み済み」。**重複の扱いは「除いて取り込む（根拠・メモは残る）」「CSVの値で上書きする（価格・損益のみ更新、根拠・メモは残る）」の2択**

### 9.7 任意項目が未入力のとき
- SLが無い → `R` と RR と想定リスクは `null`。表示は「—」。統計のR系の集計（累積R、平均R、PF、最大DD）は **R が計算できるトレードだけ**で出し、「R未計算 N件」を併記する。勝率・pips・円損益はSLが無くても全件で集計する
- ルールチェック未入力 → そのルールの判定は `na`。自動判定ルール（§9.3）も、必要な項目（SL、TP）が無いときは `na` とし、「逸脱」には数えない
- 根拠タグ別・ルール遵守別などの集計は、タグ・判定のあるトレードだけで出し、`n=` を必ず併記する。タグ無しは「未入力」の行にまとめる
- 週次レビューの「計画どおりR」は、TPが入っている手動決済だけを対象にし、対象外の件数を併記する
- エクスポートは未入力の列を空欄で出し、冒頭の集計サマリーに「SL入力あり n件 / 全 N件」「根拠あり n件」を載せる（AIが「データが少ない」ことを前提に分析できるように）

## 10. チャート

### 10.1 構成
- Frontend: `lightweight-charts` でローソク足＋EMAライン＋TP/エントリー/SLの水平破線。`features/trades/components/TradeChart.tsx`、EMA計算は `features/trades/utils/ema.ts`（純粋関数、ユニットテスト付き）。EMAは**フロントで計算**する
- Backend: **USDJPYの1分足だけを `candles_1m` に保存**し、`services/candles/resample.ts` で 5m / 15m / 1h / 4h / 1d に集計して返す（純粋関数、ユニットテスト付き）。日足・4時間足の区切り時刻は `constants/candles.ts` の1か所に置く（§15）
- EMAのウォームアップ: チャート表示範囲より前に、最長EMA期間の3倍程度の足を余分に返し、表示は範囲内だけにする
- API: `GET /candles?tf=1h&from=&to=`（認証必須。保存済みの足を返す）。トレード詳細はエントリー時刻を中心に `chart_bars_before` / `chart_bars_after` 本を要求する

### 10.2 データの入れ方（取得元は§15で確認済みの方針）
- **`CandleProvider` インターフェース**の裏に取得元を隠す:

```ts
// backend/src/services/candles/CandleProvider.ts
export interface Candle { time: number; open: number; high: number; low: number; close: number } // time は UTC の秒
export interface CandleProvider {
  fetch1m(pair: "USDJPY", from: Date, to: Date): Promise<Candle[]>;
}
```
- 実装は2つ: `DukascopyProvider`（実データ。`dukascopy-node` で1分足、時刻はUTC）と `MockCandleProvider`（決定的な疑似ランダム。テスト・取得元が未決のときの開発用）
- **同期は手元のスクリプトで行う**: `backend/scripts/syncCandles.ts`（`npm run candles:sync -- --from 2026-10-01 --to 2026-10-23`）。DBへの書き込みは、**直近48時間分は `ON CONFLICT DO UPDATE`、それより古い分は `ON CONFLICT DO NOTHING`**（再実行しても安全。取得元の直近の足は後から値が更新されることがあるため、取り込んだ直後の値を固定しない）。リアルタイム取得（`getRealTimeRates`）は使わない。過去のトレードの振り返りには不要で、取得元の公開データだけで足りる。範囲は「トレードのエントリー時刻の前後（表示本数＋EMAウォームアップ）」を全部カバーするように、CSV取り込み後に実行する。Lambdaでの自動同期は今回の対象外（STG/PRDの話になるため）
- `DukascopyProvider` を実装する前に、`dukascopy-node` が `usdjpy` の1分足（`m1`）・価格種別（bid / mid）・タイムゾーンをどう返すかを確認し、結果をPRに書く。**価格種別は既定でbid**（楽天FXのチャートと値がずれるため、確定したら持ち主が直せるよう定数化）。チャートの価格は取得元の配信値なので、楽天FXの約定価格と**わずかにずれる**（目安は1pip未満。実測してPRに書く）。その旨を詳細画面のチャート下に小さく注記する

### 10.3 失敗・データ無しの表示
- 該当期間の足が `candles_1m` に無い／APIが失敗したときは、デザイン（チャート読み込み失敗）どおりに表示する（再読み込み・別の時間足を見る）。週末・祝日の取引なしの時間帯は「データがありません」
- 開発時のみ、モックデータを使っているときは小さく「モックデータ」と出す

## 12. CSV取り込み（楽天FX証券）

### 12.1 実サンプルから分かった形式（`execution-7.csv`）

| 項目 | 内容 |
|------|------|
| 文字コード | **Shift_JIS（CP932）**。UTF-8ではない |
| 区切り・引用 | カンマ区切り、全項目がダブルクォート |
| 列 | `約定No.` / `通貨ペア` / `注文区分` / `売買` / `約定数量` / `約定レート` / `取引損益` / `取引損益（円換算）` / `注文日時` / `約定日時` |
| 行の単位 | **約定1件が1行**（新規と決済は別の行）。新しい行が上 |
| 通貨ペア | `ドル/円`（→ `USDJPY`）。それ以外は行ごとに「対応していない通貨ペア」エラー |
| 注文区分 | `新規` / `決済`。新規の行の `取引損益` は `-` |
| 売買 | `買` / `売`。**決済行の売買は決済注文の向き**（買いポジションを決済する行は `売`） |
| 数量 | 通貨単位（`10000` = 1 lot、`5000` = 0.5 lot、`1000` = 0.1 lot） |
| 日時 | `YYYY/MM/DD HH:mm`（**秒なし**、JST） |
| スワップ・手数料 | 列が無い。扱わない（§1） |
| SL・TP | 無い（取り込み後に入力） |

サンプルの実績: 2026/10/01 22:10 〜 10/23 15:21、422行、`ドル/円`のみ、新規211・決済211。数量は1万が約86%、他は5,000 / 3,000 / 1,000。

### 12.2 ペアリング
1. `約定No.` の昇順に並べる
2. 新規行を、売買ごとのキュー（買いポジション / 売りポジション）に入れる
3. 決済行は、**逆の売買のキューの先頭（FIFO）**とペアにする（決済 `売` → 買いポジション）
4. サンプルでは、この方法で211件すべてペアになり、数量の不一致も、損益の不一致（`(決済レート − 新規レート) × 数量` が `取引損益` と一致）も0件だった。**これを自動テストに入れる**（サンプルをマスクしたフィクスチャでよい。口座情報は含まれていない）
5. 新規と決済の約定Noが隣り合わないペアがある（サンプルで13件。複数ポジションを同時に持っていた）ので、**「隣の行とペア」にしてはいけない**
6. ペアにできない決済行、数量が一致しないペア、ペアにできない新規行（未決済）は次のとおり扱う: 決済に対応する新規が無い → エラー行として表示 / 数量不一致 → エラー行として表示（分割決済は対象外） / 未決済の新規 → `status = open` のトレードとして取り込む

### 12.3 トレードへの変換
- `side` = 新規行の売買（買 → `buy`、売 → `sell`）
- `entry_at` / `entry_price` = 新規行の `約定日時` / `約定レート`、`exit_at` / `exit_price` = 決済行、`exit_method = manual`（SL・TP到達かどうかはCSVから分からないので、初期値は `manual` とし、編集画面で直せる）
- `lots` = 約定数量 / 10000（1 lot = 1万通貨）
- `pnl_jpy` = 決済行の `取引損益（円換算）`
- `source = rakuten_csv`、**`source_key = "rakuten:" + 新規の約定No + ":" + 決済の約定No`**（重複判定。§9.6の「ハッシュ」案はこれに置き換える）
- 取り込み後、`sl_price` / `tp_price` / 根拠は未入力のまま（任意項目なので、そのままで構わない）。入力したいトレードだけ、キューや一覧から開いて書き足す

### 12.4 画面と処理の流れ
- 3ステップ: ① システムとファイルを選ぶ（楽天FX証券。MT5・その他は「準備中」）→ ② 内容を確認する → ③ 取り込む
- ブラウザで `TextDecoder("shift_jis")` でテキスト化 → `POST /imports/preview` に `{ files: [{ name, text }] }` を送る → バックエンドがパース・ペアリング・重複判定して結果を返す → `POST /imports/commit` で確定（重複の扱いを指定）。API Gatewayのペイロード上限（10MB）を超えるファイルはフロントで検知してエラー表示
- 別形式のCSV（`約定日時` 列が無い等）はファイル単位で「エラー」にして理由を表示し、他のファイルは取り込める
- 重複の扱いは「除いて取り込む（根拠・メモは残る）」「CSVの値で上書きする（価格・損益のみ更新、根拠・メモ・SL・TPは残る）」の2択
- 取り込み完了トースト: 「N件を取り込みました。取り込み済みM件は除きました」「入力を続ける」→ `/trades/queue`
- **件数の想定**: 約3週間で200件超（スキャルピング）。取り込みプレビュー・未入力キュー・一覧は、数百件でも遅くならないよう、サーバー側でページングと集計を行う（全件をフロントに送って絞り込まない）

## 14. フェーズ

各フェーズは**1PR**。PR前に両側で `npm run quality` と `npm run test` を通す。完了条件を満たさない状態で次へ進まない。

### P0 土台
- 依存追加、デザイントークン、`AppLayout`（統一ナビ・スマホ下タブ）、ルーティング、404
- 共通部品（Toast / ConfirmDialog / Banner / EmptyState / FieldError / UnsavedChangesGuard）
- マイグレーション 002〜004、設定API（`/settings`, `/currency-pairs`, `/tags`）、設定画面、オンボーディング
- ローカル固定ユーザー（§5.1）のフロント側迂回を追加し、Cognito設定なしで起動できるようにする
- 完了条件: **Cognito・Googleの設定なしで** `docker compose up` / SAM / Vite を起動し、オンボーディング → 設定保存まで通る。ナビが全ルートで正しい現在地を示す。PRODビルドでは迂回が無効

### P1 記録の基本
- マイグレーション 005〜007、`/rules`、`/trades` 系（CRUD・queue・restore）
- 画面: ルール、トレード記録、一覧、詳細（チャート領域はプレースホルダ）、編集・決済入力、未入力キュー
- ドメインロジック §9.1・§9.3 とユニットテスト
- 完了条件: 手入力で記録 → 後から決済入力 → 一覧・詳細に結果が出る。入力エラー・保存通知・削除の取り消し・未保存確認が動く

### P2 チャート
- マイグレーション 008（`candles_1m`）、`CandleProvider`（`DukascopyProvider` / `MockCandleProvider`）、`syncCandles` スクリプト、集計（`resample.ts`）、`GET /candles`、MFE/MAE
- 詳細画面のチャート（時間足切り替え、EMA ON/OFF・追加、TP/SL破線、エントリー後の値動き）、失敗・データ無し表示
- 完了条件: サンプルCSVの期間の1分足を同期でき、6時間足を切り替えられ、EMAを任意の期間で重ねられる。データが無い期間は失敗表示になり、再読み込みできる

### P3 CSV取り込み
- `/imports/*`、ペアリング・重複判定・エラー表示、取り込み画面（§12。サンプルCSVは受領済み）
- 取り込み後にローソク足の同期（`npm run candles:sync`）が必要な旨を、完了画面に案内する
- 完了条件: サンプルCSV（211件）が全件ペアになり、再取り込みで重複が除かれ、別形式のファイルだけが弾かれる。未入力キューにつながる

### P4 分析
- マイグレーション 009〜010、`/stats`、`/weekly-review`、`/notes`、`/rules/:id` の詳細、`/export`
- 画面: 統計、週次レビュー、学習メモ、AI分析の結果ビュー、ルール詳細、エクスポート
- 完了条件: エクスポートのMarkdownをAIに貼ると、依頼文・ルール・集計・一覧が揃っている。改善案を抽出 → ルール化 → 検証中に表示、まで通る

### P5 仕上げ
- アカウント画面、バックアップ/復元、全データ削除、退会、ログイン切れダイアログ、全画面の空状態、スマホ幅の確認、オフラインバナー（任意）
- 完了条件: デザインの全画面・全状態（空・エラー・読み込み中・成功）が実装されている

## 16. 品質と進め方

- 各フェーズの最初に、**変更するファイルと追加するファイルの一覧**を出してから実装する
- 既存コードの調査結果（再利用する共通処理）をPRの説明に書く
- テスト:
  - Backend: ユニットテスト（`test/unit/`）。`stores/` と `lib/cognito` はモック。ハンドラーの正常系・異常系、§9 の計算（境界値: SLなし、売り買い、RRが最低値ちょうど）
  - Frontend: Vitest + Testing Library。入力エラーの表示、EMA計算、未保存確認、空状態
  - インテグレーション（`test/integration/`）: trades の作成→取得、重複判定（`docker compose up -d` が必要）
- 文言・数値フォーマット: 日時は `JST` 表記、価格は小数点以下の桁数をペアのpip幅に合わせる、pipsとRには符号を付ける、数値はJetBrains Mono
- 画面の状態: すべての画面で「読み込み中 / 空 / エラー / 成功」を持つ。エラー文は「直し方まで書く」（例: 「通信を確認して、もう一度試してください。入力内容は残っています。」）

### やってはいけないこと

- `terraform/` 配下と、Terraform関連ワークフロー（`terraform-plan.yml`、`deploy-*.yml` のTerraform手順）の編集
- `001_create_users.sql` や、マージ済みマイグレーションの編集
- ハンドラーへのビジネスロジック・SQLの直書き、`stores/` へのロジックの混入
- `any`、`as any`、共通処理の再実装
- デザインにない文言・機能の追加（必要と思ったら提案として書き、実装は持ち主の確認後）
- 未決事項（§15）の推測実装
- 実データ・実口座情報・APIキーのコミット
